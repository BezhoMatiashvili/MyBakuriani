# Responsive UI Review — my-bakuriani.vercel.app

Ongoing audit of the live production site across mobile/tablet/laptop/desktop. Findings are fixed, committed to `main`, and re-verified against production after each Vercel deploy in a loop until two consecutive full sweeps come back clean.

## Methodology

- **Tooling**: no interactive browser MCP tool is available in this environment. `@playwright/test` is already a project devDependency, so a standalone script (`scripts/responsive-audit.mjs`, not part of the `e2e/` CI suite) drives real headless Chromium against the live URL.
- **Viewports**: public/auth/detail pages get the full 6-viewport matrix; dashboard/create pages (higher route count, lower marketing risk) get a reduced 3-viewport core set.

| Name             | Size      | Used for    |
| ---------------- | --------- | ----------- |
| Mobile S         | 375×812   | full + core |
| Mobile L         | 428×926   | full only   |
| Tablet portrait  | 768×1024  | full + core |
| Tablet landscape | 1024×768  | full only   |
| Laptop           | 1440×900  | full + core |
| Desktop          | 1920×1080 | full only   |

- **Auth**: dashboards/`/create/*` need a logged-in session. 9 QA test accounts (one per role: guest, renter, seller, cleaner, food, entertainment, transport, employment, admin) were created directly in the production Supabase DB via SQL (confirmed `auth.users`/`auth.identities` + `profiles` rows, no real OTP), tagged with `@qa.mybakuriani.test` emails, fake `+995500000XXX` phones, and `facade00-...` UUIDs so they're easy to find/remove later. A password-grant sign-in mints a real session, injected into Playwright as the `sb-yuwyrmxccrpfjvidwhhg-auth-token` cookie. This was explicitly authorized by the project owner after the harness flagged it for confirmation.
- **Seed data**: one property per type (apartment/hotel/for-sale villa) and one service per category (food/transport/entertainment/employment/cleaning), plus a booking/review/cleaning-task, all titled with a `QA — ` prefix so dynamic detail pages and dashboards render real content instead of empty states.
- **Diagnostics collected per route × viewport**: full-page screenshot, horizontal-overflow check (`scrollWidth > clientWidth`), interactive elements under the 44px touch-target minimum (CLAUDE.md requirement), console/page errors.
- **Review**: every route's screenshots are composited into one labeled contact sheet (`responsive-audit/sheets/<route>.png`) and visually read, not just checked against the raw overflow metric — spacing, overlap, contrast, and truncation issues don't show up in a boolean check.
- **Locale scope**: primary pass is the default Georgian locale (`ka`, unprefixed root). A handful of text-heavy pages are spot-checked afterward on `/en` and `/ru` since translated strings running longer/shorter than Georgian is a realistic overflow trigger — not a full 3-locale matrix.

## Test data cleanup

The 9 QA accounts and their seed rows (properties/services/booking/review/cleaning task) remain in the production DB for the duration of this audit loop, since repeated re-verification passes need them. They'll be removed once the UI is confirmed clean, pending confirmation.

## Active incident: Supabase Auth outage (separate from this audit)

While running the sweep, Supabase's Auth service for this project became degraded: their own logs show `failed to connect to host=localhost user=supabase_auth_admin database=postgres: dial error (timeout)`, and a plain, isolated `curl` to the auth token endpoint (unrelated to this audit's tooling) hung 20s with zero response. Since `middleware.ts` calls `supabase.auth.getUser()` on every `/dashboard/*` and `/create/*` request, this causes real HTTP 504s for real users, not just this audit. **75 of 82 dashboard/create routes returned HTTP 504 for at least one viewport during the sweep; 52 of 112 routes returned 504 at every captured viewport (0% reviewable).** This is Supabase infrastructure, not application code — not fixable here. Recommend checking https://status.supabase.com and/or opening a support ticket. The blocked routes are listed at the bottom of this doc and need a re-sweep once Supabase Auth recovers.
