# Cross-cutting Contracts

Invariants held by **string keys, generated code, or wire shapes**—couplings invisible to call-graph tools. Each is _change-one-side → must-change-the-other_. Before editing, read the section and grep repo-wide.

**Anchor:** `` `path:symbol` `` (e.g. `src/i18n/routing.ts:routing`).

## C4 — Client ↔ Edge Function wire contract

**Invariant:** `supabase.functions.invoke("<name>", { body })` couples function name and body shape (untyped). Functions in `config.toml`, bodies validated at runtime only.

**Key:** `_shared/guards.ts` bundled per-function (redeploy all 16 for changes). Rate-limiter fail-open. Exact-match CORS. Bearer token for pg_cron (`verify_jwt=false`).

**Breaks:** Function renamed (invoke string doesn't update); body field renamed (runtime 400); missing CORS origin (browser blocks); missing shared secret (cron 401s silently).

**Auth hook (C48, 2026-10-06):** `auth-send-sms` (`verify_jwt = false`) is called by Supabase Auth, never by the app: its URL and secret live in the project's Auth settings (Hooks -> Send SMS), outside the repo, so renaming the function or rotating `SEND_SMS_HOOK_SECRET` on one side only breaks every phone sign-in. It imports `_shared/ubill.ts` and `sms-automation-run/domain.ts`; redeploy it with them.

**S2/S3 (2026-09-27, staging):** every pg_cron HTTP job passes an explicit `timeout_milliseconds` (30 s; 60 s for `sms-dispatch-frequent`). `20260927090300` rebuilt the four older commands from their live text, so a new HTTP job must set its own. `check-db-contracts` C4 expects 9 active jobs (adds `keepz-reconcile-10min`, `email-dispatch-5min`, `cron-history-gc`, `pii-retention-daily`) and a missing one now FAILS. `purchase-vip` and `company-subscription` insert `payment_failed` only when `_shared/payment-failure.ts:isPaymentFailure` says the charge really failed (insufficient balance, `vip_tier_conflict`, server or network error), never on 22/23/42/P0/PGRST validation errors. **Breaks:** a schedule added without the C4 list (never checked); an HTTP job without a timeout (every run over 5 s logged as timed out); a `payment_failed` insert on a validation path (a retry loop floods the email queue).

**Ownership purge (C39, 2026-10-02):** `ownership-document-purge-hourly` (`20261001200200`, 17 * * * *, 30 s timeout) is live on STAGING since 2026-10-02 and in the C4 expected list (`check-db-contracts` now expects 10 active jobs). Vault `app.ownership_purge_url` = `https://staging.mybakuriani.ge/api/ownership-verifications/purge`; `app.ownership_purge_secret` was generated inside the database and only its SHA-256 left it, as the DO secret `OWNERSHIP_PURGE_SECRET_SHA256` (RUN_TIME). Prod: deploy the route, create both Vault entries and the env var, then apply (the migration refuses with 22023 while a Vault entry is missing; without the env var the route answers 503 and every run fails).

**SMS dispatch cadence (2026-10-03, `20261003100000`, STAGING):** `sms-dispatch-frequent` runs every minute (`* * * * *`, was `*/10`). The dispatcher only polls (nothing calls it when a row is queued), so the schedule is the queue-to-provider latency: at `*/10` a user-triggered SMS went out 2-10 minutes after the action (staging 2026-10-01/02: 2-599 s from `created_at` to `submitted_at`, `available_at` = `created_at` on every row), and a row another job queued in the same tick (`sms-automation-daily`, the Keepz sweeper crediting a top-up) could land just after that tick's claim and wait the full ten (599 s, twice). After the change a probe row was claimed 32 s after its INSERT by the next tick. The migration only calls `cron.alter_job` for the schedule (live command and 60 s timeout untouched) and refuses with 55000 where the job is missing; `check-db-contracts` C4 matches job names, not schedules. Overlapping runs are safe (advisory lock + 15-minute lease in `sms_claim_dispatch_batch`, `FOR UPDATE` duplicate branch in `sms_mark_provider_delivered`); each run makes one uBill brand lookup and re-polls `submitted` rows older than 15 minutes (none stuck on staging). Prod has the same `*/10` job (read-only look 2026-10-03, unchanged), so the migration does not refuse there and the next prod migration sync switches it to every minute; prod's dispatcher answers `delivery_enabled:false` and its `sms_outbound` holds 4 rows ever (none sent), so each extra run is a cheap no-op. Other hops keep their own cadence: all 3 top-ups credited on staging so far (2026-09-27 to 10-02) were credited within 2 s of a `keepz-reconcile-10min` tick, so a top-up's `payment_success` notification (and its SMS) appears up to 10 minutes after the payment (that sweeper also re-polls the 3 declined payments on every run, `checked:3` at 11:30:00, so a faster Keepz cadence multiplies those calls), and `email-dispatch-5min` polls every 5 minutes. **Breaks:** a re-run of `20260801132000` (puts `*/10` back); a faster schedule without re-checking the per-run uBill calls; code that assumes an SMS leaves seconds after its INSERT (the floor is the 60 s poll, and uBill reports delivery about 60 s after submit).

## C5 — Storage bucket names

**Invariant:** Bucket id in upload code, migration+RLS, and image/CSP allow-list. Buckets: `property-photos`, `avatars`, `landing-media`, `restaurant-menus`, `content-change-media`.

**Breaks:** Bucket renamed in code only (upload 403 or Image blocked); RLS missing on new bucket.

**S2 (2026-09-27, `20260927090200`):** `property-photos` client INSERT only at `<auth.uid()>/<file>` (exactly one folder level). There is no client UPDATE policy: uploads stay `upsert:false` and never move, copy-overwrite or `update()`. DELETE is owner-only; service-role writers bypass RLS. **Breaks:** an uploader writes into a subfolder or a listing-id folder (42501, shown as `uploadFailed`); an upsert/move/update call without a new UPDATE policy pinned to folder AND bucket (UPDATE policies OR across buckets, so a loose one re-opens cross-bucket moves).

**Menu PDFs (2026-10-01):** `restaurant-menus` takes only `application/pdf` up to 10 MiB (`file_size_limit` 10485760) and the bucket checks nothing else. The food form (`create/food/page.tsx`) judges a menu by its bytes through `src/lib/menu-pdf.ts:readMenuPdf`, never by `file.type` (Chrome derives it from the extension): non-empty, `%PDF-` inside the first 1 KiB, a `%%EOF`/`startxref` trailer in the last 4 KiB (or anywhere in the file unless it is linearized), at most `MAX_MENU_PDF_BYTES`. `onPickMenuFile` runs it for early feedback beside the field (the footer error is below the fold on desktop). `uploadMenuPdf` is the gate: it reads the input's own current file first (Chrome fires no `change` when the same path is picked again after a re-save, which leaves the React-held `File` stale), checks again and uploads the bytes it just checked, never the live `File`. A gate refusal empties the input when it still holds the refused file (so the same path can be picked again; a newer pick survives) but keeps the tile, so a plain second Publish is refused again instead of quietly dropping the menu (in edit mode: a saved one). `MAX_MENU_PDF_BYTES` must equal the bucket limit; `scripts/unit/menu-pdf.test.mjs` compares it with the bucket migration. `check-contracts.mjs` C5 fails any `src` file whose literal `.from("restaurant-menus").upload(` does not store the bytes of a `readMenuPdf` result: it wants `const X = await readMenuPdf(…)` within 700 characters of code before the call and `X.bytes` written inside the call's arguments (a pick-time call nearby, a dropped result, the live `File`, a helper doing the upload and a body built before `.upload(` all fail; comments don't count, strings do; uploads through a constant, `.update()` or a signed URL are not seen). **Known limits:** the check is structural, so mid-file damage, zero-page and password-protected PDFs pass, and so does a cut-short copy that mentions `startxref`/`%%EOF` in its body; a complete linearized PDF with 4092 or more bytes after its last `%%EOF` is refused; in edit mode a good pick followed by a rejected one leaves neither file nor link, so Publish queues `menu_url: null` for admin review (C14); a pick, X or typed link made while Publish is in flight is ignored (the file read at Publish is the one stored, and the gate's read widens that window by up to 10 MiB of reading); there is no server-side byte check, so an API client can still store any object up to 10 MiB declared as `application/pdf`; no committed test covers the form's refusal behaviour (tile kept, input read first, conditional clear), so change it only with a browser check. **Breaks:** an uploader that trusts `file.type` or sends the live handle stores a 0-byte or cut-short object that `services.menu_url` then points at (staging 2026-10-01: Chrome showed "Failed to load PDF document"); the cap changed on one side only.

**ownership-documents (C39, 2026-10-02, `20261001200000`):** private, 10 MiB, pdf/jpeg/png/webp, and NO `storage.objects` policy at all — browsers never read or write it. Only the service-role upload route writes it (`upsert:false`, server-chosen type, `cacheControl: "60"`), admins view a file through a 60 s signed URL without `download`, and only `src/lib/ownership/purge.ts` deletes from it. **Breaks:** any storage policy naming the bucket (ID cards become client-readable); a second deleter.

**finance-documents (C42, 2026-10-05, `20261005120000`):** private, 10 MiB, pdf/jpeg/png/webp, and NO `storage.objects` policy. Only `POST /api/admin/finance/documents` (service role, `upsert:false`, bytes screened by C39's `checkOwnershipDocumentBytes`, object name = the row id) and the issued-invoice archive (`archiveInvoicePdf`) write it; admins open a file through a 60 s signed URL without `download`; the only removal is the upload route deleting its own object when the row insert failed. **Breaks:** any storage policy naming the bucket; a second deleter (documents are voided, never deleted).

## C6 — CSP & external origins

**Invariant:** Every external host in both CSP directive AND `remotePatterns`. No build error—only runtime block.

**Key CSP moved to middleware.** Mapbox GL needs `worker-src 'self' blob:`. Supabase, unsplash, Mapbox, Turnstile, rtsp.me allowed. **Breaks:** Add CDN without CSP (image 404, fetch blocked); add to CSP only (Image blocked); a hard-coded or wildcard Supabase host; a new Supabase origin (custom domain, `<ref>.storage.supabase.co`) not added to media-hosts.ts; the URL env var scoped BUILD_TIME only (the optimizer 400s every photo).

## C42 — Finance & tax reporting module (admin, staging)

**Invariant:** every finance number has ONE SQL definition, and every page, export and PDF reads it. `finance_ledger_v` is the effective money movement (cash basis): a Keepz payment counts when `status='succeeded' AND credited_at IS NOT NULL`, dated `completed_at`; a Keepz refund when `succeeded`, dated `resolved_at`; manual income when `completed`, dated `occurred_at`; refunds, adjustments and reversals signed. `finance_monthly_totals()` buckets it by Asia/Tbilisi month; `finance_tax_year()` and `finance_vat_window()` build on that. The registers are `finance_payments_v` (every attempt; the revenue journal = `RECEIVED_PAYMENT_STATUSES` only — an attempt is never revenue), `finance_refunds_v` and `finance_invoices_v` (derived paid/overdue). Nothing financial is edited or deleted: a mistake is reversed by a mirror row in the same period.

**Symbols:** migrations `20261005120000_finance_module.sql`, `20261005120100_finance_invoice_vat_rule.sql`, `20261005120200_finance_audit_index.sql` (partial `audit_logs` index for the history route: 215 ms → 0.2 ms on staging); tables `finance_settings` (one row), `finance_entries` (income/refund/adjustment/owner_payout/reversal), `finance_expenses`, `finance_documents` + private bucket `finance-documents`, `invoices`, `invoice_counters`, `invoice_templates`; pure `src/lib/finance/{constants,filters,money,xlsx}.ts`, server `src/lib/finance/pdf.ts` and `src/lib/finance/server/{data,http,labels,reports,invoices}.ts`; `/api/admin/finance/*` (summary, payments, refunds, owners, entries[/id], expenses[/id], documents[/id], invoices[/id][/pdf], invoice-templates[/id], tax, vat, settings, audit, export) and the public `/api/invoices/[token]`; UI `src/app/[locale]/dashboard/admin/finances/**` (own sub-menu `src/components/admin/finance/FinanceNav.tsx`) and `src/components/admin/finance/*`; namespaces `AdminFinances` + `AdminInvoices` (`DASHBOARD_NAMESPACES`, C1).

**Key:**

- **Who owns the money:** a manual income carries `owner_amount`, the third party's share (500 ₾ received, 450 ₾ the owner's, 50 ₾ MyBakuriani's); taxable = amount − owner share; `finance_owner_payables()` = collected − refunded − paid out. Keepz payments carry no owner share (wallet top-ups and platform purchases). Revenue types come from `finance_intent_revenue_type(resume)` (Keepz) or the entry; a top-up is `wallet_topup` cash when credited, and spending the wallet later (`finance_wallet_usage()`) is shown apart, never added again. `finance_wallet_reconciliation()` compares `transactions` with `balances` (staging 2026-10-05: 50 ₾ apart on one wallet).
- **Tax (informational, not an RS declaration):** `finance_tax_year()` applies Tax Code art. 90 as amended 27.12.2023 — the base rate, and the higher rate from the START of the month in which the calendar year's taxable income passes the threshold, to year end (defaults 1 % / 3 % / 500 000 ₾, editable in `finance_settings`). VAT watch: `finance_vat_window(as_of)` = own taxable income of the 12 calendar months ending with as_of's month against 100 000 ₾ (art. 165: registration within 2 working days) — an approximation to confirm with an accountant.
- **Append-only:** `finance_forbid_delete` triggers on entries, expenses, documents and invoices (service_role keeps Supabase's default table privileges, so the trigger is the guard); `finance_entries_guard` / `finance_expenses_guard` / `finance_documents_guard` / `invoices_guard` freeze rows, copy a refund's or reversal's details from its original, cap refunds and payouts, and refuse reversing an income with live refunds. Ids: FE-n (`entry_no`), EX-n, DOC-n (identities, gaps allowed), invoice numbers `<prefix>-<year>-<seq>` from `invoice_counters` locked at issue (no gaps among issued numbers). Every write goes through `createServiceClient(adminId)` so `trg_audit_row` records the admin (`/api/admin/finance/audit`).

Issued PDFs are archived to `finance-documents` (idempotent; "archive PDF" retries).
- **Secure link:** only the SHA-256 of a 32-byte token is stored; 30 days; every share or send replaces the previous link; `/api/invoices/[token]` serves the PDF only while issued/sent and unexpired (30 per 10 min per IP, `no-store`, `X-Robots-Tag: noindex, nofollow`; the middleware's app-wide Referrer-Policy replaces the route's own, as in C39).
- **E-mail:** the link only, straight through Resend (C33 switches checked before the link is replaced; not through `email_outbound`, so outside its retries and `EMAIL_DAILY_CAP`); 30 per hour per admin.
- **Exports (spec §13):** `/api/admin/finance/export?report=<REPORT_KEYS>&format=csv|xlsx|pdf&<filters>` builds from the same `*Ops` filter definitions as the register pages (`data.ts`), always in Georgian (`financeT`, locale ka): CSV with BOM, XLSX from `xlsx.ts` (inline strings, money format, frozen header), PDF from pdf-lib + Noto Sans Georgian (Cyrillic transliterated, other missing glyphs `?`). - **Documents:** see C5. A document proves at most one record (entry, expense, invoice, payment or refund) and is voided with a reason, never deleted.
- Registers page at 50 rows; register totals are sums over the whole filter (`fetchAll`), the payments register has none (attempts are not money).

**Known limits:** VAT turnover is approximated by own taxable income on a cash basis; Keepz payments are classified by their `resume` intent (no owner share); the invoice e-mail is not queued or capped; PDF fonts carry no Cyrillic; no RS e-invoice integration; manual names are snapshots (a renamed account keeps its old name on old rows).

**Guards:** `check-contracts.mjs` C42 (12 CHECK lists = `constants.ts`, document limit = bucket, pure modules without `@/`, finance tables and the bucket written only under `src/app/api/admin/finance/` and `src/lib/finance/server/`, the public link hashed + noindex, one filter per register), `check-db-contracts.mjs` C42 (`finance_contract_snapshot()`: RLS, no anon/authenticated/PUBLIC grant on tables, views or functions, private bucket, no storage policy, the 14 triggers enabled, CHECK lists = constants), `scripts/unit/finance-{money,xlsx,filters,messages}.test.mjs` (pricing equals `invoices_guard`, XLSX package, Tbilisi dates, every label and `FINANCE_*` error worded in ka/en/ru).

**Prod order:** after the C32 Keepz batch (`payments`/`payment_refunds` with `resume`, `credited_at`, `review_flag`): apply `20261005120000`, `20261005120100` and `20261005120200`, deploy the app, then fill the issuer details in Finances → Settings before issuing an invoice.

## C44 — Admin status management: memberships, VIP / SUPER VIP, discounts, company plans (staging)

**Invariant:** an admin changes an existing status only through three SECURITY DEFINER RPCs (`20261006120000`, service_role only, called only from `/api/admin/statuses/**`): `admin_change_memberships`, `admin_change_listing_promotions` and `admin_change_company_plans`. Apply sends the identical body with `dryRun: false`. The form enables it only while the inputs equal the previewed ones, and a failed or unanswered apply drops the preview (the statement may have committed; ±days must not be re-sent blindly).

**Symbols:** migration `20261006120000_admin_status_management.sql` (status CHECK, `trg_audit_row` on `organization_subscriptions`, `_admin_status_*` helpers, views `admin_membership_overview_v` / `admin_listing_promotions_v` / `admin_company_plans_v`, the three RPCs); `src/lib/admin-statuses.ts` (pure: vocabularies, limits, parsers, Tbilisi dates, error tokens); `src/lib/admin-statuses-server.ts` (RPC call, error mapping, filter plumbing, cache bust); `GET|POST /api/admin/statuses/{memberships,listings,companies}` (GET: filters, counts, `?ids=1` select-all), `GET /api/admin/statuses/memberships/[userId]` (every period, refundable amounts); UI `/dashboard/admin/statuses` (`src/components/admin/statuses/*`); namespace `AdminStatuses` (`DASHBOARD_NAMESPACES`, C1); nav key `DashboardSidebar.nav.statuses`.

**Source:** the owner's "MyBakuriani_Advertising_Media_Plan_Rate_Card_v1.0" (2026-10-06): an ad is sold on a slot, a period and a share of voice (SOV); §7 lists the campaign fields (placement, start/end, SOV/weight, priority, frequency cap, creative, click URL, impressions, clicks, CTR, status) and says 100 % SOV excludes every other ad of the slot. **Key:**

- **The draw (§4):** SOV slots are NOT normalised — a lone 25 % ad wins about a quarter of page views (priority high→low, then share, then id; an oversold slot squeezes the lowest priority), the rest goes to house fill (the first editorial banner) or nothing. `listing_grid` splits every sponsored position between the booked ads by weight. The first two draws win, so the landing page's server-fed slots (`home_hero`, `home_promo`) claim before the store-fed `mobile_strip`: with ads drawn in both, the strip yields on `/` (its empty position is counted, so its actual SOV shows the loss); on listing pages the strip and `listing_top` draw before the grid card (measured locally 2026-10-06 with three 100 % ads per page). Visitor data is first-party and consent-gated (C38): only a visitor with `analytics=1` gets `page_views` / `analytics_events` rows and the `mb_vid` / `mb_sid` cookies. Only derived categories are stored, never a User-Agent, a referrer URL or an IP.

**Key:**

- **Page.** `/dashboard/admin` keeps the pending-verification alert and "ბიზნესის მაჩვენებლები" (net revenue, registered users, occupancy, average nightly price, bookings and completed stays of 7 days, from `admin_overview_stats`). The lifetime visit and visitor cards, the active-listings card and the 7-day funnel were removed (the owner's choice, 2026-10-06), and the dead "სტატისტიკის გადმოწერა" button became the whole-page export. Below come the toolbar (period §1, filters §8, and the active choices as the spec's chain "ბოლო 30 დღე → Mobile → თბილისი → Google → Export"), then KPIs (§2), the chart (§3), traffic sources (§4), Live Now (§9), listings (§5), Smart Match (§6) and advertising (§7). Each block loads on its own and has its own export menu. Country names come from the server (`src/lib/analytics/cities.ts:countryNames`, Node's full ICU data, handed down through `CountryNamesContext`): Chrome has no Georgian region names, so on its own it writes "GE" or "Georgia" on a Georgian page.
- **Collection.** `PageviewTracker` posts each allow-listed public page view (`pageview.ts`, which now also allows `/bakuriani`, `/pricing` and `/marketing-policy`) with the landing signals: the external referrer host, `utm_*`, `gclid`/`fbclid` flags and `maxTouchPoints`. It keeps the returned row id and reports the page's visible time once, by `sendBeacon` to `/api/track/ping`, when the page is hidden or left. It also sends a keepalive every 120 s while the tab is visible and was used in the last 2 minutes (Live Now). `analytics_ping` adds at most 5 minutes per call to the caller's own row only: `mb_vid` must own it, the row must be under 6 h old, and a row holds at most 4 h. It also stamps `last_seen_at`. Key actions go to `analytics_events` in two ways. `events.ts:recordAnalyticsEvent` is called inside `after()` once the action succeeded: `listing_view` only when the view beacon counted it (C22), `call` / `message` from the contact route's `channel`, and `job_application`. With analytics consent, the listing view beacon (`useListingViewCount`) is sent only after the page view has been answered (`track-client.ts:afterPageview`, at most 2.5 s). The page view issues the cookies, so the first page of a visit or of a session (typically a listing reached from Google) still records its visitor and source. `/api/track/event` takes `save` only for a favorites row of the caller and `smart_match_request` only for the caller's own request. Load: one extra beacon per page view, plus at most one ping per 2 minutes per active tab, all uncached.
- **Session (`mb_sid`).** The cookie is `<uuid>.<source>.<device>`, HttpOnly, Lax, with a rolling 30 minutes (view and ping refresh it). A new session starts when the cookie expired, or when a hit arrives with an external signal of another source (`continuesSession`, GA's rule). The source is Google, Facebook, Instagram (including the in-app browser), referral (any other external host) or direct (`traffic-source.ts`); a session keeps the source of its first hit. Page views from before the release got sessions by the same 30-minute gap rule (deterministic ids); their source, device and location stay NULL ("not recorded").
- **Person (§10).** One unique user is the `user_id` when signed in. Otherwise it is the one account its `mb_vid` was ever signed in to (`analytics_person_map_v`; a browser seen with two accounts stays the cookie). Otherwise it is the cookie. It is never the IP. Sessions, users and page views are separate counts.
  - Active = a person with an engaged session (≥ 10 s visible, ≥ 2 page views, or a lead event).
  - New = their first hit ever falls in the period.
  - Returning = Unique − New.
  - Engagement rate = engaged sessions ÷ sessions.
  - Key Actions / Leads = `call + message + smart_match_request + job_application` events (`LEAD_EVENTS`). They come from consenting visitors only, so they can be lower than the Listings block.
- **Filters (§8)** cut every block except two:
  - Advertising follows the period only, because C46 holds no visitor data.
  - The inventory facts are "not applicable": active = `status='active'` now, and new = created in the period, so they describe listings, not visitors.

  With a filter, Listings and Smart Match count `analytics_events` (consenting visitors, from the release on). Without one, they count their domain tables: `listing_view_events`, `favorites`, `contact_reveal_events`, `smart_match_requests` and `smart_match_offers`.
  - Device = User-Agent + `maxTouchPoints` (an iPad reports as a Mac).
  - Country and city come from `geoip.ts` on `getClientIp` (C16), over DB-IP Lite: country worldwide, city inside Georgia. The IP is looked up, never stored. A city filters only together with its country (`analytics_check_dims`, the query parser), but the toolbar lets the admin pick the city straight away: its country comes with it, and the chain shows the city alone, as in the spec's "Mobile → თბილისი → Google".
  - Page type = `analytics_page_type(path)`.

- **Definitions (the owner's choice, 2026-10-06):**
  - Calls = phone-button reveals and messages = WhatsApp-button reveals (`channel`); older reveals are "not split".
  - Matching listings = distinct listings that offered on the period's requests.
  - Match rate = requests with ≥ 1 offer ÷ requests.
  - Responses = offers that were not cancelled.
  - Leads = offers followed by a contact from that guest on that listing.
  - Advertising = `admin_banner_analytics(…, 'ad', …)` (impressions, `reach` in devices, clicks, CTR = clicks / impressions, per placement; C46/C47) plus `admin_analytics_ads`. That covers active ads by the live predicate and the distinct `ads.advertiser` among them. The ad form's "რეკლამის დამკვეთი" sets the advertiser, `parseAdvertiser` cleans it, and the block shows how many live ads have none. Revenue = `finance_ledger_v` advertising, amount − owner share (C42, cash basis).
- **Periods (§1):** Tbilisi days, inclusive, at most 366 (`MAX_RANGE_DAYS` = `analytics_check_range` = the C46 cap). Compare uses the same number of days just before. Chart buckets are day, ISO week (Monday) or month.
- **Live Now (§9):** people whose latest hit or ping is under 5 minutes old, the pages they are on and the latest rows. The block refreshes every 15 s while the tab is visible and follows the filters, not the period. A visitor who closes the tab stays listed up to 5 minutes (the last ping).
- **Export (§11):** every block and the whole page (`block=all`), in scope `filtered` (period and filters) or `full` (same period, no filters). Formats are XLSX (one sheet per section, `src/lib/finance/xlsx.ts:buildXlsxWorkbook`; `buildXlsx` output is unchanged), CSV (BOM, titled sections) or PDF (`src/lib/finance/pdf.ts:renderReportPdf`, additive to C42). Every file names the period, the comparison, the scope, the active filters ("none", or "not applicable" for ads), the granularity, the generation time (Tbilisi), the consent note and the DB-IP attribution. The file text is in Georgian, as in C42. Every XLSX sheet starts with those lines, and every PDF page repeats the period and the generation time in its footer (`AnalyticsReport.stamp`; the spec wants them in the tables, not only on page 1). Limits: 60 exports per 10 minutes per admin; the data route allows 240 a minute.
- **Retention and grants:** see C37 (`analytics_events.user_id` after 90 days, so stitching and signed-in identity reach 90 days back) and C34 (service_role only).

**Known limits:**

- Consent-gated, so every visitor number is a lower bound.
- Device, location and source exist from the release on; the filter note says since when.
- DB-IP places most Georgian mobile carriers in Tbilisi.
- A save that was later undone is missing from the unfiltered saves, because favorites rows are deleted.
- Leads need `contact_reveal_events.account_id`, which is scrubbed after 90 days (C37).
- `mb_sid` is a second analytics cookie. The privacy policy's §2.3, §2.4 and §5 already name session data, identifiers, device data and analytics cookies, without cookie names.
- Advertisers depend on admins filling the field: until then the block shows 0, with the count of live ads that have none.
- New users come from every person's first page view ever, a scan of all of `page_views` on each traffic call. A year on staging (1.9k rows) took 125 ms and prod holds 851 rows (2026-10-06). If the table reaches hundreds of thousands of rows, keep a first-seen table instead.

**Breaks:**

- A vocabulary changed on one side only: the route answers 400 or the RPC 22023, and the C49 check fails.
- A writer of `page_views` / `analytics_events` that skips the consent check: identifiers for a visitor who declined.
- Storing the UA, the referrer URL or the IP.
- A second `mb_sid` writer, or a session rule outside `continuesSession`.
- An `admin_analytics_*` call outside `server.ts`, or a loader import without `requireAdmin`.
- A client grant on the table, the view or the functions.
- The DB-IP link or the export line removed (CC BY 4.0).
- Country names read only from the browser's `Intl.DisplayNames`: in Chrome a Georgian page shows "GE" in the country filter, its chip and Live Now.
- A number computed in TypeScript instead of in the SQL: the page, the export and the PDF disagree.
- `MAX_RANGE_DAYS` changed without `analytics_check_range`.
- The app deployed before the migration: the view route's insert names columns the database lacks, so every page view is lost (503), and the admin analytics answer 500.
